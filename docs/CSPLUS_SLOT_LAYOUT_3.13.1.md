# CS+ E2 车位跳变排查：v3.13.1

## 结论

跳变的主要原因是结构体对齐错误。当前 S73 / RH850 E2 调试符号对应 4 字节对齐：车位数组从偏移 4 开始，每项 44 字节，整体 268 字节。上位机此前固定采用 8 字节头、48 字节步长、296 字节总长，将不断变化的 64 位时间戳切成了有符号坐标，表现为数十米的巨型车位跳动。

同时，旧有效判定只统计非零坐标分量，没有按 `left_slot_num` / `right_slot_num` 限制槽位。当原始数量为 0 时，上述错位值也被发布。两项问题均在上位机修复，未修改或烧写实车工程。

## 实机证据

通过 CS+ `debugger.Address` 读取当前成员地址：

- `sf_Upper_SlotOutSignal`：`0xFE4033CC`。
- `left_slot_info[0]`：`0xFE4033D0`，相对偏移 4。
- `left_slot_info[1]`：`0xFE4033FC`，相邻步长 44。
- `right_slot_info[0]`：`0xFE403454`，相对偏移 136 = 4 + 3 × 44。
- 第一个 info 的 `slot_F_type` 在 info 内偏移 40，成员布局与 42 字节解包格式一致，尾部填充到 44。

读取的原始头部为 `[2, 0, 0, 0]`，左右车位数都为 0。按 4/44 解码，六项坐标与尺寸都为 0，时间戳约 `1767226956979335`，A/F 类型被固件置 1。按旧 8/48 解码，时间戳的一部分落到坐标中，例如 `(7303, -26878)`，后续样本变成 `(26484, -26858)`、`(-6882, -26806)`。这种变化直接来自时间戳字节，不能通过调整坐标单位修复。

原始 40 次采样及旧解码保存在 `build/slot-investigation/slot-layout-and-samples.json`。修复后连续 30 次读取成功，车位数量和有效绘图项均保持 0，记录为 `fixed-live-slots.json`。

地址仅用于说明本次编译产物，程序每次连接仍通过调试器解析，不能将地址硬编码到其他版本。

## 修复行为

支持 `(header, stride)=(4,44)` 和 `(8,48)`，用数组成员及尾字段地址共同校验；连接级缓存避免逐帧查询符号。预取使用相应 268 / 296 字节长度，布局未知时拒绝猜测，防止继续画错坐标。

左右各仅显示声明数量以内的前三项；过滤全零、重复为单点和包含 0x7fff / -32768 无效坐标的槽位，原始毫米值保持不变。两种布局均使用合成有效车位验证尺寸、左右索引和坐标，未在本次现场人为制造停车场景或写入目标内存。

此前 v3.12.1 / v3.13.0 验证中记录的“6 个车位”来自旧解析，不能作为真实车位数据有效的证据；点云、线段、连接及性能测试结论分别成立。
